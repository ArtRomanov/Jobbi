# Discovery worker (`python -m app.discovery`)

Hourly check of vacancy sources → pre-AI keyword filter → Groq evaluation → Inbox → Telegram alerts. Run one instance only.

- **Pre-AI keyword filter** (`keyword_filter.py`, `service._apply_keyword_filter`): before each user's evaluation, pending posts (not `needs_detail`, not forwarded to the bot) whose title and text name none of `VacancySearchSettings.keywords` are deleted without an AI call; the seen key stays with `filtered_at` (never comes back, even after a keyword change) and `RunReport.posts_filtered` counts them. A keyword matches at the start of a word (no left boundary when it starts with a symbol: ".net" ~ "ASP.NET"), any case, no right boundary ("фронт" ~ "фронтенда"); spaces/hyphens inside it match any run of spaces/hyphens. The delete re-checks "not forwarded"; forwarding a filtered post clears `filtered_at` and stores it as new (`_unfilter_seen_key`). Off when `keyword_filter_enabled` is false or the list is empty. Skipped in the per-minute forwarded-only run. The Sources panel shows `filtered_at` in the last 24 h.
- **Stale pending expiry** (`service._expire_stale_pending`, backlog #19): runs right before the keyword filter, same conditions (hourly run only, not `needs_detail`, not forwarded — re-checked in the DELETE). A pending row is deleted without an AI call when older than `STALE_PENDING_AFTER` (= `LOOKBACK`, 7 days): `tg:` keys by `posted_at`, every row by `found_at` (board/web `posted_at` is the employer's date, may be old for a job just found). Seen key stays, no marker (no migration); `RunReport.posts_expired`, logged as `expired=`. Reads the clock once per user.
- **Pending count per source** (`vacancy_source_service.pending_counts`): `VacancySourceRead.pending_count` = the user's `pending` rows of that source (not `needs_detail`, same rule as the Inbox banner's `_count_waiting`; forwarded rows have no source), one grouped COUNT per GET; shown as "Waiting for AI: N".
- **Evaluation order** (`service._fair_order`, backlog #19): forwarded posts first, then round-robin over sources (`ROW_NUMBER() OVER (PARTITION BY source ORDER BY posted_at DESC)`), freshest first; equal `posted_at` → first found first. At most `PER_SOURCE_RUN_LIMIT` (20) posts of one source per run (`evaluate_pending` call), counted across batches in `_UserEvaluation`; the rest stay pending (`RunReport.posts_deferred`, logged `deferred=`). Forwarded posts and rows without a source are never capped. The daily cap stays the overall limit.
- **Source kinds and fetchers** (`fetchers/`): `telegram` (`telegram.py`); `greenhouse` / `lever` / `lever_eu` / `teamtailor` / `ashby` via `board_scan.py` (`greenhouse.py`, `lever.py`, `teamtailor.py` — RSS through `lxml` with entities and network off, `ashby.py` — Posting API JSON); `web` via `web_scan.py` (`web_listing.py` parses a listing, `web_job.py` reads one job page).
- **Site listing adapters** (`fetchers/site_listing.py`): for a known site whose listing is a JS shell (now: geekjob.ru search links with a filter), `read_listing` reads the site's JSON endpoint via `safe_http.fetch_json` instead of the HTML; same page limit and stop rules, everything after the listing unchanged. Add a site = add a matcher to `_MATCHERS`; its parser must never raise.
- **Blocked sites:** `safe_http` maps a bot challenge (403/429/503 + `cf-mitigated: challenge`, or Cloudflare challenge markup) to `PageFetchError("blocked")`; board APIs (`board_http`) map `cf-mitigated: challenge` to `BoardReadError("blocked")`; one text `errors.BLOCKED_MESSAGE` ("This site blocks automated readers") for the API and the worker; the detail step stops a source at its first challenged job page. Geekjob sources are stored by the adapter's `canonical_url` (`vacancy_source_service.parse_input`).
- **Web = two steps.** Listing step: up to 5 pages, stops after the first page with a seen key; new jobs are stored `pending` + `needs_detail`. Detail step: up to 30 job pages per source per check (JSON-LD `JobPosting`, else `trafilatura.extract`); after 3 failed reads the row is evaluated by its listing title. The evaluator skips `needs_detail` rows.
- **safe_http rule:** every user-supplied URL (API preview/save/edit and the worker) goes through `fetchers/safe_http.py` (public IPs only, pinned IP, every redirect re-checked, 15 s / 5 MB caps). Never call `trafilatura.fetch_url` or a plain `httpx` client on such URLs — only `trafilatura.extract` on HTML already fetched by `safe_http`.
- **Seen-key formats** (`vacancy_seen_keys.external_key`): `tg:<channel>/<post_id>`, `gh:<token>/<id>`, `lever:<company>/<id>` (`lever_eu:` for EU), `tt:<subdomain>/<job_id>`, `ashby:<org>/<job uuid>`, `web:<source_id>/<sha256(normalized job url)>` — keyed by source id, so history survives a link edit.
- **Groq models:** `GROQ_DISCOVERY_MODEL` (gpt-oss-20b) rates posts; `GROQ_DISCOVERY_FALLBACK_MODEL` (gpt-oss-120b, "" = off) takes over when the primary answers a **daily** 429 (TPD/RPD in the message; quotas are per model). `evaluator.ModelChooser` (one per process, held by `DiscoveryConfig.models`) remembers until Groq's "try again in …" / `retry-after` time (default 15 min) that a model is out (a non-finite wait → the default, any wait capped at 24 h); a 404 `model_not_found` on the fallback logs one ERROR and drops the fallback until restart; a fallback equal to `GROQ_MODEL` logs a startup warning; `evaluate_with_fallback` repeats the same request on the next model. Per-minute 429 (TPM/RPM) → no fallback, run stops as before; both models out → `EvaluationRateLimitedError(daily=True)`, run stops, `ai_failing_since` set. Only gpt-oss gets `reasoning_effort`; never use the chat (qwen) model as fallback. Each batch logs "rated by <model>" (info, no post text).
- **First scan window:** 7 days (`LOOKBACK`) for boards. A Telegram channel's first scan reads back to 7 days but at most 4 pages (~80 posts, `TELEGRAM_FIRST_SCAN_MAX_PAGES`) and sends only the last 3 days (`TELEGRAM_FIRST_SCAN_LOOKBACK`) to the AI; older posts are recorded as seen only. Otherwise the next hourly read would bring them back as new, alerted cards: an hourly read (7 days, 10 pages) stops after the page that holds a known post but keeps that page's unknown posts.
- **Alerts** (`alerts.send_run_alerts`, once per run, per user; cards `new`/`seen` with `alert_handled_at IS NULL` among the run's `new_card_ids`): hourly-check cards → one "🔎 N new vacancies" message. First-scan cards (`from_initial_scan`, stored with `alert_handled_at` NULL since backlog #30; older rows were stored handled and stay so) → grouped by `Vacancy.source_id` (outer join to `VacancySource`): ≤ `MAX_SEPARATE_SOURCES` (3) sources → one message per source ("🔎 New channel <name>: N matching vacancies", "New source" for non-Telegram kinds, link `<inbox>?source=<url-encoded kind:handle>`); more → one combined message ("🔎 New sources: N matching vacancies from M sources", per source "<name> (N)" + its lines). Same 10-line cap and "+M more in Inbox" as the hourly text. A first-scan card rated in a later run (daily cap, per-source cap, AI down) is summarised by that run. Source removed → handled, no message. Every loaded id is marked handled in every case (no bot, no link, send failure); read → send → short write. Telegram posts outside the 3-day first-scan window are never cards, so never mentioned.
- **No network inside a DB transaction:** fetch first, then a short write transaction, then commit.
- **Revision guard:** `VacancySource.revision` grows on every edit that changes what is fetched. `_SourceRef` carries the revision it was loaded with; stores add `AND revision = :rev` (rowcount 0 → results dropped), and the detail step checks `_revision_unchanged` before each write.
- **First-scan lease:** `_take_initial_lease` sets `initial_attempt_started_at` before a first-scan attempt; `_release_initial_lease` clears it. While set, the API refuses edits with 409; a lease older than `ATTEMPT_LEASE_TTL` (10 min, e.g. a crashed worker) is ignored.
